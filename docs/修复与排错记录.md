# 修复与排错记录

本文档记录了 DeskWeek 近期的架构重构、功能修复、典型问题排查以及性能验证情况。

---

## 一、核心优化与修复汇总

| 模块 | 优化与修复内容 | 实际效果 |
| --- | --- | --- |
| **数据安全保存** | 采用写入临时文件再安全替换的方式，并在保存时自动生成 `.backup` 备份文件 | 避免断电或程序异常退出时损坏日程文件；主文件损坏时可自动从备份恢复 |
| **双窗口协同** | 管理中心与桌面浮窗同时编辑任务时，智能对比数据基准 | 自动合并不同字段的修改；如果同时修改了相同文字，弹窗提示确认，避免无意覆盖 |
| **多屏幕适配** | 依据所有可用显示器的工作区范围校验浮窗坐标与尺寸 | 支持跨屏幕自由拖拽与不同缩放比例（DPI）；拔插屏幕或改变分辨率时自动修正回屏幕内 |
| **桌面异常恢复** | 监听 Windows 桌面宿主状态，在桌面环境重启时自动重建浮窗 | 即使 Windows 资源管理器崩溃重启，浮窗也会自动恢复，并保留正在输入的文字草稿 |
| **全屏节能休眠** | 检测到任意屏幕有全屏应用（如游戏、全屏视频）或锁屏时暂停刷新动画；长时间全屏时释放界面资源 | 大幅降低全屏打游戏和后台闲置时的 CPU 与内存占用；退出全屏后即刻自动恢复 |
| **显卡覆盖层识别** | 完善全屏判定逻辑，检查后台窗口的真实透明度与窗口交互属性 | 准确识别 NVIDIA 录屏滤镜、DisplayFusion 等后台透明辅助窗口，彻底解决浮窗误休眠问题 |
| **窗口生命周期管理** | 在消息通信与加载回调中增加窗口存活校验，窗口关闭时自动清理旧监听 | 彻底解决快速切换或频繁休眠唤醒时偶发的 `Object has been destroyed` 报错 |
| **文件解析内存控制** | AI 文档解析任务放置在独立的后台工作线程中运行，并设置内存限制与 30 秒超时保护 | 解析大文件或异常格式文档时不会卡死主程序，任务结束或超时后自动回收系统资源 |
| **安全自动更新** | 升级前校验安装包的 SHA-256 完整性，更新过程备份原有文件并保留 `data/` 目录 | 确保更新包安全可靠，如安装过程中断可平滑回滚，保障用户日常数据安全 |
| **模块化代码拆分** | 将主进程按桌面、窗口、运行策略、存储、IPC、AI、更新等清晰模块化，样式与组件分层组织 | 提高代码可读性与可维护性，便于后续添加新功能 |

## 二、典型显示问题排查与解决

在测试和日常使用中，曾定位并解决了两个关于桌面浮窗的典型问题：

### 问题 1：启动后浮窗正常显示，但约 15 秒后突然消失

- **现象描述**：
  在桌面启动浮窗后，浮窗能正常显示，但过了约 15 秒浮窗自动消失，托盘图标依然正常；点击托盘“显示浮窗”后，浮窗出现不久又再次消失。
- **排查与根因**：
  系统开启了 NVIDIA 显卡录屏覆盖层或 DisplayFusion 辅助工具。这些工具在后台生成了一个尺寸几乎覆盖整个屏幕的辅助窗口。旧版全屏检测只检查了窗口的大小，误将该透明窗口判定为“用户正在全屏打游戏”，从而触发了自动节能休眠，在 15 秒无操作后释放了浮窗界面。
- **修复方案**：
  在全屏检测逻辑中增加了更精准的规则：
  1. 排除系统任务栏、被系统隐藏的窗口以及自身窗口。
  2. 针对分层窗口，进一步检查其是否真正完全透明。
  3. 排除不接收键盘焦点的后台工具型覆盖窗口。
  修复后，全透明辅助层不再被误判，浮窗能在各类后台覆盖层运行下持续稳定显示。

---

### 问题 2：全屏切回时偶发报错 `Object has been destroyed`

- **现象描述**：
  当用户快速频繁地切换全屏应用、或在浮窗重新加载的极短瞬间进行操作时，可能会弹出一个包含 `TypeError: Object has been destroyed` 的错误提示框。
- **排查与根因**：
  这是由于快速切换导致的窗口关闭与页面加载回调的时序冲突。旧窗口已经被关闭销毁，但稍早触发的页面加载回调（`did-finish-load`）随后才执行，此时回调代码尝试向已销毁窗口的 `webContents` 发送消息，从而引发系统报错。
- **修复方案**：
  引入统一的窗口生命周期防护层（`src/main/windows/lifecycle.cjs`）：
  1. 向任何窗口发送消息前，先校验窗口及其内部页面对象是否仍然存活。
  2. 窗口关闭时，立即解除并清理原有的加载监听器。
  3. 状态广播与通知严格校验接收窗口的有效性。
  经过真实模拟连续 20 次极端快速切换测试，该异常已彻底消除。

## 三、测试命令与验证方式

项目包含完整的自动化测试套件，在项目根目录运行以下命令即可执行相应验证：

| 测试命令 | 验证内容说明 |
| --- | --- |
| `npm run check` | 检查全部 JavaScript 源码语法正确性 |
| `npm test` | 核心逻辑自动化测试（数据读写、多屏几何计算、文件解析、全屏识别规则等） |
| `npm run test:host` | Windows 桌面集成测试（双屏移动、双窗口协同编辑、草稿保存、全屏休眠恢复） |
| `npm run test:visibility` | 真实桌面可见性测试（验证后台第三方工具不会导致浮窗误隐藏） |
| `npm run test:resume` | 连续休眠与恢复压力测试（验证频繁休眠唤醒时的窗口稳定性） |
| `npm run test:appearance` | 外观渲染测试（深浅主题、全透明背景效果与控件对比度） |
| `npm run test:packaged` | 对最终打包生成的便携程序进行完整功能验证 |

## 四、内存与资源占用实测

在实际 Windows 环境下，对 DeskWeek 进行了运行内存（工作集）采样，结果如下：

| 运行阶段 | 浮窗界面状态 | 总体内存占用 | 说明 |
| --- | ---: | ---: | --- |
| **日常正常使用** | 渲染器正常运行 | 约 500 MB | 包含主进程、Chromium 渲染引擎、GPU 加速与日历界面 |
| **全屏休眠状态** | 渲染器自动释放 | 约 370 MB | 全屏玩游戏或锁屏时，浮窗界面自动卸载，节省约 130~140 MB 内存 |
| **切回桌面恢复** | 渲染器重新加载 | 约 500 MB | 退出全屏后 1~2 秒内自动重新绘制界面，恢复正常使用 |

> **说明**：后台始终保留极轻量的主进程与托盘服务，以便随时监听系统全屏状态并在退出全屏时立刻唤醒。如果浮窗中有尚未保存的文字输入，程序会优先保护用户数据，不会强行释放界面。

## 五、使用建议与注意事项

为了获得更好的使用体验，建议注意以下事项：

1. **打包与日常使用隔离**：打包生成新版本时，建议通过环境变量或独立文件夹输出，避免输出路径指向日常正在使用的 `data/` 目录。
2. **编辑及时保存**：输入框中的未保存文字在软件运行期间有自动暂存保护，遇到系统桌面重置能自动恢复；但在主动退出或重启电脑前，建议点击保存按钮。
3. **动态壁纸重叠处理**：若被某些动态壁纸软件意外覆盖，右键托盘图标点击“找回浮窗并重置位置”即可快速唤回最前。
4. **虚拟桌面协作**：管理中心支持识别 Windows 虚拟桌面，打开管理中心时会自动优先复用当前桌面中的窗口。
5. **网络更新排查**：检查更新通过 GitHub 官方接口，如遇网络连接超时或 403 提示，可直接前往 Releases 页面手动下载最新压缩包解压覆盖。

## 六、新增外观特性：全透明浮窗模式

在“管理中心 → 设置 → 浮窗背景”中新增了 **“透明”** 选项（默认为标准卡片风格）。

- **视觉特点**：开启透明模式后，浮窗会隐藏白色卡片底板、边框和阴影，仅保留日历网格、待办文字以及必要的交互图标，呈现纯粹轻巧的视觉效果。
- **自动适配壁纸**：支持配合浅色主题（深色文字）或深色主题（浅色文字），无论浅色还是深色壁纸都能清晰阅读。
- **弹窗体验优化**：编辑任务和日期选择时，会使用柔和的半透明深色浮层，确保文字清晰易读。
- **设置即时同步**：该选项会自动保存在本地配置中，管理中心修改后桌面浮窗即刻同步生效。
